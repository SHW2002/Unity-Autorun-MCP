# Unity Autorun Tool

[中文（默认）](./README.md) | [English](./README_EN.md)

Unity Autorun Tool automates Unity Editor workflows using reusable C# business scripts. An external AI reads the host project's sources and runtime evidence, Unity compiles and executes the scripts, and MCP exposes script management, tracked results, UIState, and basic interactions.

## Quick installation

Requires Unity 2021.3 or newer, [Git](https://git-scm.com/downloads), and the [.NET 8 SDK](https://dotnet.microsoft.com/en-us/download/dotnet/8.0).

1. Open `Window > Package Manager` in Unity.
2. Select `+ > Add package from git URL...` and enter:

   ```text
   https://github.com/SHW2002/Unity-Autorun-MCP.git
   ```

3. Wait for import and compilation, then open `Window > Auto Run Window`.
4. Expand `Connection > MCP Settings & Diagnostics`, then press `Tools > Publish MCP` to build the current server.
5. Under `Install` in the expanded section, select the project's `.codex` or Claude Code `.claude` directory, then press `Install MCP` and `Install Skills`.
6. To make agents check existing scripts before game/UI self-tests, press `Install Agent Rules` in the separate `Agent Rules` row. It writes instructions to `AGENTS.md` at the current host Unity project root, independently of the client directory and `Install Skills`.
7. Reconnect the AI client. Confirm `Bridge` is `Running` and `Processes` shows its MCP process. `Versions` displays separate MCP, `gen-script`, `edit-script`, and `run-script` versions and installation states.

`Install Skills` installs all three independent Skills into `.agents/skills/` beside the selected `.codex` directory, or into `.claude/skills/` for Claude Code. It validates and stages the whole batch before replacing installed versions, rolls back the entire batch on an exchange failure, and refuses to overwrite a newer installed Skill. Existing `unity-autorun` installations are preserved with a manual removal notice so custom changes are not deleted.

For Claude Desktop, select the directory containing `claude_desktop_config.json` and install MCP only. The Desktop target does not load filesystem Skills from that directory.

## Host Agent Rules and self-test selection

The `Agent Rules` row shows the host `AGENTS.md` as `Not installed`, `Update available`, `Current`, or a read/marker error, with a refresh action. Use `Install Agent Rules` or `Update Agent Rules` to write the instructions; an unchanged block shows `Agent Rules Current`. Writing requires clicking install or update. The selected client directory never changes the host destination.

Fixed markers `<!-- unity-autorun:agent-instructions:begin -->` and `<!-- unity-autorun:agent-instructions:end -->` surround a versioned block. A missing file or block is created/appended. An update replaces only the managed block and preserves all user rules outside it. Duplicate markers, a missing counterpart, incorrect ordering, or a newer block version return an error without overwriting the file.

The instructions require agents to call `list_scripts` and `get_script(includeSource=true)` before game/UI operation self-tests and verify the starting state, complete flow, assertions, parameters, and dependencies. Run a valid matching script directly with `run-script`. When none matches, never silently create a script; ask whether the user wants a self-test script created. An explicit creation request or `gen-script` invocation already authorizes creation and needs no repeated confirmation. Unavailable MCP, Unity, or Bridge calls block discovery and do not prove that no script matches. Wrong starts and failed runs retain the game state and produce evidence; agents must not change the flow, weaken assertions, or reset the game on their own.

## Generate and self-test a script

```text
$gen-script From the home UI after starting the game, open inventory, assert that the currency text is nonempty, and save a screenshot
```

`gen-script` defines the starting state, exact flow, parameters, and success assertions; inspects existing business and basic scripts; and creates C# source under the host project's `Assets/Editor/AutorunScripts/`. Unity compiles the new code before a self-test. Failed self-tests allow up to three repair rounds by default, restricted to code generated by the current task.

Scripts in the previous `Assets/AutorunScripts/Editor/` directory remain discoverable, readable, and manageable. New sources use the Editor directory. Existing files are not moved automatically; use `AssetDatabase` to preserve their `.meta` and GUID when moving them.

Reuse requires the entire business segment to match: its starting conditions, actions, and outputs must be identical. A common destination is insufficient. Reused scripts are never edited to fit the new task. Different starting states or flows to the same target receive different script IDs and source files.

Every business script declares `Preconditions` and overrides `CheckPreconditions`. A wrong starting state fails before actions; the script does not silently select another flow. Cold-start scripts declare `PreparePlayMode = true` in their attribute: the runner enters Play Mode before checking the actual starting scene/UI, without a GUI toggle or caller flag. Declare and call the `start-play-mode` basic script to reuse preparation verification. Other scripts may explicitly use caller `ensurePlayMode=true`, whose default remains false. A child's preparation declaration never starts its parent flow or switches Play Mode during execution.

## Edit an existing script

```text
$edit-script Fix currency text reading in business.open-inventory while preserving its starting state, inventory-opening flow and nonempty-currency assertion; compile, self-test and inspect affected callers
```

`edit-script` inspects the requested existing business source, dependencies, and reverse callers, defines the maintenance scope, and checks `unity_status.data.scriptRunStateAvailable=true`, `data.hasActiveScriptRun=false`, and `data.isCompiling=false` before changing code or refreshing. Wait while runs or compilation are active or run status is temporarily unavailable; report persistent missing/unavailable status as a blocker. Unknown state must never be treated as idle. It preserves the original starting state, complete flow, and goal contract and edits only the requested script. Reused dependencies and basic scripts cannot be changed to fit the task. A different start, flow, or goal needs a separate ID and file generated with `gen-script`; ask first if creation is not already authorized.

After editing, refresh Unity, check compilation and registration errors, self-test with a new `runId`, and regression-test affected callers from their own declared starts. Repairs allow up to three rounds by default and never weaken preconditions or assertions. Missing starting conditions, unavailable Unity/Bridge, and blocked caller regressions are reported as actual blockers and unverified results. The Skill does not implicitly cancel active runs, reset the game, or stop Play Mode.

## Run an existing script

```text
$run-script Run the inventory script just generated and verify its final UI state
```

`run-script` finds and inspects an existing script's starting conditions, dependencies, and parameters; runs it; waits for the terminal result; and verifies assertions. It does not generate or modify scripts. A missing matching flow, wrong starting state, or failed assertion produces a concrete result with run evidence.

All three Skills allow normal automatic discovery and explicit `$gen-script`, `$edit-script`, or `$run-script` invocation. Their self-contained installable packages are [`skill~/gen-script/`](./skill~/gen-script/), [`skill~/edit-script/`](./skill~/edit-script/), and [`skill~/run-script/`](./skill~/run-script/); none relies on paths outside its installed folder.

## Editor script management

The `Autorun Scripts` panel includes:

The default view shows script names, the run action, and a short result. Scripts declaring `PreparePlayMode=true` show an automatic startup hint and `Start Game & Run` in Edit Mode. Other scripts expose `Start game first` beside the run action. Active runs show their latest step log; completed runs append their final result to Console, and failures are shown directly. Expand `Script Details` for descriptions, starting conditions, sources, and dependencies; `Run Options` for parameters and timeout; and `Result Details` / `Recent Runs` for calls, logs, artifacts, and history. Errors and cancellation remain visible. MCP settings and Console start collapsed.

The catalog and filtered choices are cached and updated after compilation or an explicit refresh. Focusing the window does not rescan the project, and idle run history does not trigger continuous repaints. Process and binary version queries run in the background; periodic process queries stop while MCP settings are collapsed.

- Business/basic categories, name and ID search, and source opening.
- Declared starting conditions, nested dependency trees, callers, and missing dependency, duplicate ID, cycle, or registration errors.
- String-valued parameter JSON, explicit Play Mode preparation, timeout, run, and cancellation.
- Recent results, nested invocation states, logs, and screenshot artifacts.
- Business source deletion through `AssetDatabase` after dependency checks and user confirmation. Basic scripts cannot be deleted from the panel.

Success, failure, timeout, and cancellation preserve the current game state and Play Mode, releasing only resources owned by the script. Stop the game through an explicitly requested `unity_stop` or `stop-play-mode` action.

The old navigation map, graph preview and route calculation, `gen-nav`, and manual XML navigation presets have been removed. Existing host-project data is not automatically migrated or deleted; future workflows use scripts.

## C# script contract

Use MCP `get_script_guidance` for the current contract and template. Inspect the host `.asmdef` layout before generating: scripts need an Editor assembly that references `UnityAutorunTool.Editor` and the actual host API assemblies. If host APIs live in predefined `Assembly-CSharp`, keep scripts in predefined `Assembly-CSharp-Editor`; a new `.asmdef` cannot reference `Assembly-CSharp`. Public types are in `UnityAutorun.Scripting`:

```csharp
using System.Collections;
using UnityAutorun.Scripting;

[AutoRunScript("business.check-current-ui", "Check current UI", AutoRunScriptKind.Business,
    Description = "Assert that the declared starting UI exists.",
    Preconditions = "Play Mode; query identifies the expected current UI.")]
public sealed class CheckCurrentUi : AutoRunScript
{
    public override string CheckPreconditions(AutoRunScriptContext context)
    {
        if (!context.Host.IsPlaying) return "Play Mode is required.";
        if (string.IsNullOrWhiteSpace(context.GetString("query"))) return "Provide query.";
        var state = context.Host.EvaluateUiState(new AutoRunScriptUiStateQuery
        {
            Query = context.GetString("query"), Exact = true, Comparison = "exists"
        });
        return state != null && state.Ok && state.Matched ? null : "Starting UI does not match.";
    }
    public override IEnumerator Execute(AutoRunScriptContext context)
    {
        context.Log("Starting UI assertion passed.");
        yield break;
    }
}
```

Supported yields are null, nested `IEnumerator`, `context.Wait`, `context.WaitUntil`, and `context.Call`. `WaitForSeconds`, `WaitForEndOfFrame`, and Unity Coroutine handles are unsupported. Read parameters with `GetString/GetInt/GetNumber/GetBool`; dependency parameters must be passed explicitly and are not inherited.

Declare every `context.Call` target in the attribute's `Dependencies`. Missing dependencies, duplicate IDs, cycles, and undeclared calls fail. `OnExit` releases subscriptions and temporary objects owned by the script without resetting the scene or stopping Play Mode.

`start_script(ensurePlayMode=true)` saves the initial preparation request while no actions have executed, so it can continue across the Domain Reload caused by entering Play Mode. After preparation, it checks the declared starting state and runs the business script once. An already running C# iterator cannot be restored across Domain Reload; do not directly toggle Play Mode or trigger recompilation from a business iterator. Unexpected reload during execution retains a terminal failure rather than replaying completed actions.

| Built-in ID | Purpose | Common parameters (string values) |
| --- | --- | --- |
| `start-play-mode` | Prepare initial Play Mode entry before a root run, then verify startup; a business root declares `PreparePlayMode=true` | None |
| `click-button` | uGUI/FairyGUI button click | `name`, `text`, `objectPath`, `scope`, `framework`, `matchPolicy` |
| `wait` | Real Editor time delay | `seconds` |
| `wait-for-ui-state` | Wait for an observable assertion | `query`, `scope`, `property`, `comparison`, `expected`, `timeoutSeconds` |
| `screenshot` | Capture Game View and record a saved artifact | Optional `path`, `timeoutSeconds` |
| `stop-play-mode` | Explicit game stop | None |
| `log` | Run log entry | `message` |

Screenshots default to the host project's `AutorunToolData/Screenshots/`. uGUI requires a button name or text, with observed paths/scopes narrowing candidates; prefer unique matches. Clicks check the current `EventSystem`, interactability, and raycast target before dispatching pointer events. FairyGUI supports only a unique button name and rejects text/path/scope selectors.

## MCP and CLI

Script tools are `get_script_guidance`, `list_scripts`, `get_script`, `create_script`, `refresh_scripts`, `start_script`, `get_script_status`, and `cancel_script`. Use live schemas. Bridge endpoints are discovered dynamically through the host project's `Library`; diagnostic port discovery is usually unnecessary.

The optional `UNITY_AUTORUN_BRIDGE_PROFILE` environment variable isolates endpoint discovery for a Bridge instance:

| Setting | Endpoint file relative to the host project root |
| --- | --- |
| Unset or empty string | `Library/UnityAutorunTool/bridge-endpoint.json` |
| Simple name such as `preview` | `Library/UnityAutorunTool/profiles/preview/bridge-endpoint.json` |

A profile is 1–64 ASCII letters, digits, hyphens, or underscores; whitespace and directory paths are rejected. Configure the same profile for Unity before the Bridge's first initialization and for the MCP process. Unity stores the first profile used in this Editor session, including an empty value, in `SessionState` separately for each Bridge assembly. It remains unchanged across Domain Reload, so later environment changes do not redirect that assembly's Bridge publication or cleanup. An invalid profile, or a missing or stale endpoint for the selected profile, returns an error without falling back to the default or an older instance's endpoint.

`create_script.path` is relative to `Assets/Editor/AutorunScripts/` and existing files are never overwritten. After `refresh_scripts`, wait for `unity_status.isCompiling=false`, inspect `compilerMessages`, and check registration errors before execution.

Asset refresh, script-service initialization, and Bridge restoration after reload are scheduled on the main thread through `EditorApplication.update`. An unfocused Editor does not need an Inspector update to trigger `delayCall`. Refresh requests return before the subsequent Editor update handles them; wait for compilation and asset import to finish before inspecting the actual result.

`start_script` takes `scriptId`, string-valued `parameters` or `parametersJson` (choose one), `timeoutSeconds`, `ensurePlayMode`, and optional `runId`. Transport retries of one execution reuse its ID; conflicting retries are rejected. Intentional new runs and self-tests after repair use new IDs because an old ID returns the retained result. `get_script_status.data.scriptRun` contains state, code, message, call stack, logs, and artifacts, including on failure. A preliminary observation of a wrong start can be reported without execution; do not claim a runner-generated failure when no run was started.

```powershell
dotnet run --project mcp~/UnityAutorun.Mcp -- help
dotnet run --project mcp~/UnityAutorun.Mcp -- status
dotnet run --project mcp~/UnityAutorun.Mcp -- script-guidance
dotnet run --project mcp~/UnityAutorun.Mcp -- list-scripts --kind business
dotnet run --project mcp~/UnityAutorun.Mcp -- get-script --script business.check-current-ui
dotnet run --project mcp~/UnityAutorun.Mcp -- start-script --script business.check-current-ui --parameters-file parameters.json
dotnet run --project mcp~/UnityAutorun.Mcp -- script-status --run <runId>
dotnet run --project mcp~/UnityAutorun.Mcp -- cancel-script --run <runId>
```

UI tools remain available: `unity_status`, `unity_play`, `unity_stop`, `list_buttons`, `click_button`, `run_sequence`, `is_ui_view_open`, `get_ui_state`, and `wait_for_ui_state`. UIState covers uGUI Text, InputField, Toggle, Slider, Dropdown, Scrollbar, ScrollRect, Button, Image, RawImage, and optional TextMeshPro controls. It exposes values, paths, activity, visibility, and interactability; it does not replace pixel layout or animation review. Password fields are masked by default.

## Build and publish

```powershell
dotnet build mcp~/UnityAutorun.Mcp -c Release
dotnet run --project mcp~/UnityAutorun.Mcp.Tests -c Release
dotnet publish mcp~/UnityAutorun.Mcp -c Release
```

Published MCP files are under `mcp~/UnityAutorun.Mcp/bin/Release/net8.0/publish/`. Release archives are under that project's `bin/Release-Archives/`, named `UnityAutorun.Mcp-platform-packageType-yymmdd-hhmmss.zip`.

The Editor `Publish MCP` action matches MCP processes by their full binary path, stops those processes, waits for DLL unlock, publishes, and checks client reconnection. Unrelated `dotnet` processes are preserved. Direct `dotnet publish` does not manage existing MCP processes; disconnect the affected client or use the Editor action when a published DLL is locked.

The .NET tests do not compile Unity Editor code or generated host scripts. Host compilation, self-tests, screenshot capture, and actual starting-state assertions still require Unity validation.

## Troubleshooting

- Compilation pending: inspect `unity_status` and Unity Console, wait, then refresh scripts.
- Script missing: check the host `Assets/Editor/AutorunScripts/` path, public class, attribute, parameterless constructor, IDs, and dependency errors.
- Wrong start: prepare the exact declared starting state or generate a separate flow; do not edit shared scripts to hide the difference.
- Click failure: inspect hierarchy, blockers, interactability, EventSystem, and selector precision.
- Reload or Play Mode stopped during execution: inspect the retained terminal result. The runner does not restore arbitrary iterators or replay completed actions.
- Stale Skill tools: update `gen-script`, `edit-script`, and `run-script`; review custom changes in an installed legacy `unity-autorun` before manually removing it.
- Agent Rules error: inspect paired, unique begin/end markers in the host root `AGENTS.md`, preserving user content outside them; a newer rules version needs a tool version that supports it.
